# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Standalone WordPress plugin ("AI Translator for Polylang & WPML"; slug and text domain `ai-polylang-translator`): AI translation of posts, products, terms and ACF fields into other Polylang or WPML languages via Vercel AI Gateway. No Composer, npm, or test runner. Requires PHP 8.1+, WordPress 6.0+, Polylang or WPML active (not both); ACF, Yoast SEO and WooCommerce are optional integrations. See AGENTS.md for contribution conventions.

## Commands

```bash
# Lint (run after every change — the only automated check)
php -l ai-polylang-translator.php
find includes -name '*.php' -exec php -l {} \;

# Multilingual boundary: must print nothing (only includes/lang/ may call Polylang/WPML)
grep -rnE "pll_|PLL\(|wpml_|icl_|SitePress|WCML|'lang' *=>" --include='*.php' . | grep -vE '^(\./)?includes/lang/'

# In a local WordPress install
wp plugin activate ai-polylang-translator
```

Manual verification happens in wp-admin: Settings > AI Translator (API-key test, model select, cost log), and the "AI Translation" metabox on a post (new translation, overwrite confirmation, safe mode, retry). Test on a Polylang site and on a WPML site (see README.md, Testing), with and without ACF/Yoast/WooCommerce active.

## Architecture

Bootstrap `ai-polylang-translator.php` defines constants, detects the multilingual plugin (`AIPT_Lang_Loader::detect()`), loads one `AIPT_*` class per file from `includes/`, instantiates `AIPT_Settings` + `AIPT_Metabox` + the bulk page (`AIPT_Bulk_Ajax`, `AIPT_Bulk_Page`) in admin, registers the adapter's hooks, the `AIPT_Auto` hooks and `AIPT_Block_Refs`' `render_block_data` filter in every context (admin, REST, cron, CLI, front end), and registers `AIPT_CLI` as `wp aipt` when WP-CLI is running. Without a usable adapter (neither plugin, or both Polylang and WPML active) it shows an admin notice and loads only the settings page. `assets/` is dependency-free vanilla JS/CSS.

### Multilingual adapter (`includes/lang/`)

Every multilingual-plugin call goes through `aipt_lang()`, the `AIPT_Lang` implementation the loader picked (`AIPT_Lang_Polylang` or `AIPT_Lang_WPML`; design and WPML facts in `docs/plans/wpml-support.md`). Nothing outside `includes/lang/` may call the multilingual plugin (boundary grep above). `translation_state()` returns `none` / `translated` (Polylang) or also `pending` (never written: prepare, CLI and auto skip it like a locked pair) and `duplicate` (overwritten in full: no safe mode, not skipped by `skip_existing`, auto translates it). Mutating calls (`begin_post`, `commit_post`, `link_term`) return `true|WP_Error` and verify the link; on `aipt_link_failed` the writer deletes a post it created in this run unless the backend already resolves it as the source's translation (deleting a group member could cascade), while such a linked post or an updated existing post keeps its content and is reported with its ID. At the end of every write the writer runs `clean_post_cache()` and fires `do_action('aipt_translation_written', $post_id, $source_id, $lang, $created)`, after meta, Woo attributes, ACF and terms are in place (for page caches and site code). `block_text_attributes()` returns the block text-attribute keys the backend already parsed from `wpml-config.xml` (WPML: its `wpml-gutenberg-config` option; Polylang: `[]`, `AIPT_Block_Attrs_Config` then reads the files itself). Jobs carry `backend` (adapter name) and `schema` (2): a job from another backend is refused, a job without `backend` (pre-1.6) only runs on Polylang.

### WPML adapter (`includes/lang/class-aipt-lang-wpml.php`, `-wpml-tm.php`, `-wpml-sync.php`)

WPML owns languages, groups, TM status and WCML sync; the adapter only uses WPML's public hooks/globals (cited file:line in the code) and fails with `aipt_wpml_api` when one is missing. Write flow: `suspend_sync` first checks the WPML API (and WCML's sync hook when WCML is active), then removes `$wpml_post_translations` `save_post`@100 and WCML's save hook; any failure returns a `WP_Error` and the writer refuses before inserting (`aipt_sync_missing`, with the adapter's message). The new post stays without a language until `commit_post` links it into the source's trid via `wpml_set_element_language_details` (never taking over another post, a TM placeholder or a group member), verifies, re-checks pending TM work for the pair (also when the target was already linked; on pending it returns `aipt_target_pending` without touching the TM status), deletes `_icl_lang_duplicate_of`, fires `wpml_tm_save_post` (TM status complete/local), switches the group's original to the native editor (setting `native_editor`, Advanced panel, default on), marks the translation as native-edited for WPML Page Builders (else PB regenerates its body from the original's strings), runs WPML Media's image translation for it, runs `wcml_synchronize_product_translations` for products, cleans the post cache, re-applies the suspension (WCML re-adds WPML's handler) and verifies again. `translation_state`: `pending` = placeholder row or an in-progress `icl_translation_status` for the pair (also over an existing post; a query error counts as pending), `duplicate` = target has `_icl_lang_duplicate_of` or TM status 9. Read-only `icl_*` queries are allowed only inside `includes/lang/`. `wpml-config.xml` keeps `_aipt_auto_scheduled` / `_aipt_auto_user` out of WPML's custom-field sync. Term elements are `term_taxonomy_id`s; every `get_term()` in the adapter runs with `wpml_disable_term_adjust_id` (WPML otherwise swaps terms for their current-language translation outside wp-admin), and new terms are inserted and linked inside `in_language($target)`, while the source side of `AIPT_Terms` (existing-translation checks, ancestors, names/descriptions) runs inside `in_language($from)`. `languages()` includes hidden languages (`SitePress::get_languages(default, true)`). `refresh()` calls `reload()` on WPML's group caches and flushes the runtime object cache (`AIPT_Pipeline::flush_runtime_cache()`); `translation_state()` reads the target's duplicate meta uncached.

### Global switch

`enabled` in `aipt_settings` (default on; `AIPT_Settings::enabled()`, a raw option read). Off parks the plugin: no metabox and `guard()` refuses every AJAX step, `AIPT_Auto` neither schedules nor runs queued events, `wp aipt` refuses to start and a running bulk command re-reads the option between records (`translate`: before each post × language; `translate-terms`: before each taxonomy × language, so term batches already sent to the API complete) and stops with exit status 1. The settings page, cost log and API-key test keep working.

### Translation pipeline: prepare → translate_batch (loop) → finalize

Implemented in `AIPT_Pipeline` (each step returns data or `WP_Error`; the job payload is built by `AIPT_Job_Builder`). `AIPT_Metabox` is a thin AJAX layer over it (nonce/capability `guard()`, `$_POST` parsing, job ownership (durable bulk job ids are refused: they only go through the bulk layer), `wp_send_json_*`; response shapes are what `assets/metabox.js` expects). `AIPT_Pipeline::translate_post()` runs the same steps in-process for WP-CLI and auto-translation: it owns the pair lock for the whole record (holder `cli` or `auto`), re-checks the existing translation under it when `skip_existing` is set, and keeps batch results in memory (no job/batch transients; usage still recorded per batch). Every `AIPT_Writer::write()` call goes through `AIPT_Pipeline::write()`, which sets `is_writing()` and puts the `_aipt_auto_scheduled` marker on the written post:

1. **prepare** (`ajax_prepare`): `AIPT_Extractor::extract()` collects translatable strings, `build_batches()` greedy-packs them (8 KB / 60 items per batch), and `AIPT_Job::create()` stores an **immutable** job payload in a transient (TTL 1 hour). The job snapshots the model at creation time so the cost log reflects the model actually used.
2. **translate_batch** (called per batch index): `AIPT_Gateway::translate_map()` sends an `{id: text}` JSON map to the model and expects the same keys back. Each batch's result + token usage is saved in its **own** transient (`AIPT_Job::save_batch`) so concurrent batch requests never read-modify-write a shared blob. Idempotent: a finished batch returns success without re-translating. Usage is recorded immediately after the API call (tokens are billed even when the reply is rejected).
3. **finalize** (`ajax_finalize`): merges all batch transients, takes a DB-row finalize lock, and `AIPT_Writer::write()` creates/updates the translation post. On success a small completion marker is kept so duplicate finalize calls return the link.

### WP-CLI (`AIPT_CLI`)

`wp aipt translate` selects source IDs up front (`AIPT_Select`: `fields => ids` in the source language, parents first) and processes one post × language at a time: pre-checks composed from `AIPT_Record` (`check_source`, `missing_parent`, `translated_terms` + `missing_terms`; dry-run planning via `AIPT_Runner::estimate` with an `AIPT_Runner_Context`) → `translate_post(holder: cli)`; every record gets one TSV log line (`AIPT_CLI_Log`, which also owns the summary and exit status). `wp aipt translate-terms` delegates to `AIPT_Terms::translate()` (names/descriptions via `AIPT_Gateway`, linked terms created parents first, dry-run price, rows streamed through a callback so output appears as in 1.4.0; descriptions are sanitized by us with `wp_kses_post` for users without `unfiltered_html` and inserted with core's inline-only `pre_term_description` kses lifted, so block HTML such as `<h2>`/`<div>` survives). New terms need the taxonomy's `edit_terms` capability: `translate()` reports `skipped_no_permission` otherwise, and the CLI refuses up front. Flag parsing lives in `AIPT_CLI_Args`; cost estimates use `AIPT_Settings::price_per_char()`. See `wp help aipt translate`.

### Bulk groundwork (1.7, Phase 1)

`AIPT_Runner` holds the shared record policy used by the CLI and the bulk admin page: `precheck`, `new_post_status`, `estimate` (with a serializable `AIPT_Runner_Context` of planned posts/terms for chunked estimates) and `revalidate_before_write` (source still exists/eligible, publish rule recomputed, parent/terms/capabilities re-checked, `aipt_source_changed` on a changed `post_modified_gmt`). Jobs created with the `durable` prepare option get `d-<uuid>` ids and live in non-autoloaded options (`aipt_djob_*`, `AIPT_Job_Store`) until `AIPT_Job::delete()`; editor jobs stay transients. `translate_batch` runs under a per-batch named lock (`aipt_batch_<job>_<n>`, TTL 4×timeout+60; `AIPT_Job::with_named_lock`, which also releases on shutdown) and returns `reused` and `usage`. Finalize (`AIPT_Finalize`) saves `stage => finalizing` before the writer for durable jobs only (a durable job found at that stage under the finalize lock returns `aipt_finalize_interrupted` instead of writing again), and the outcome after it (`status => complete`, `finalized_id`, `warning`, `outcome` = `AIPT_Pipeline::outcome_status()`; `stage` exists only while finalizing); durable jobs keep only a small completion marker (`MARKER_KEYS`); `AIPT_Pipeline::job_stage()` gives none/finalizing/complete. The writer tags every written post with `_aipt_job` and the auto marker right after insert/update (`AIPT_Pipeline::write()` puts both in the payload as `tag_meta`); both metas are excluded from Polylang/WPML meta sync.

### Bulk admin page (1.7, `AIPT_Bulk_Page`, `AIPT_Bulk_Ajax`, `AIPT_Bulk_Request`, `AIPT_Bulk_Jobs`, `AIPT_Bulk_Terms`, `assets/bulk.js` + `bulk-run.js` + `bulk-ui.js`)

Settings > AI Bulk Translation (`manage_options`, slug `aipt-bulk`). One page nonce `aipt_bulk`; every action runs `AIPT_Bulk_Request::guard()` (nonce, `manage_options`, `AIPT_Settings::enabled()`, an API key, then `ignore_user_abort(true)`); input validation and the JSON response also live in `AIPT_Bulk_Request`. Actions (`wp_ajax_aipt_bulk_*`): `taxonomies` (term counts per taxonomy of `AIPT_Bulk_Terms::choices()` — translated taxonomies of the enabled types with `edit_terms`, all rendered by the page — in the `from` language; `bulk.js` loads them on load and when From changes and disables a taxonomy with 0 terms), `plan` (validated post types ⊂ settings, translated taxonomies with `edit_terms`, from/targets; returns term pairs and `AIPT_Select::posts(…, ['publish'], …)` rows `{id, parent}`, parent = `post_parent` for every type, since `AIPT_Record::missing_parent()` checks it for every type; `AIPT_Runner::estimate` plans every new translation likewise), `estimate` (`items`: records `[{id, lang}]`, or with `terms=1` term pairs; `AIPT_Runner::estimate` / dry-run `AIPT_Terms::translate` until ~8 s, carrying the `AIPT_Runner_Context` array; returns `rows` and `next`), `terms` (`AIPT_Bulk_Terms::slice`: from `offset` in the parents-first source order, the next terms without a target translation that pack (`AIPT_Terms::items` + `AIPT_Extractor::build_batches`) into ≤ 2 gateway batches (at most 120) are created at once under the named lock `aipt_bulk_terms_<tax>_<lang>`; returns rows, `existing`, `next` (null = done), `remaining`, `error_code` = the gateway code of a failed row, which `AIPT_Terms` puts in the row as `code`), `prepare`, `batch`, `finalize`, `discard`, `pending`, `reset`. A source the user may not edit is `aipt_source_forbidden` (that record fails; the guard's `aipt_forbidden` is fatal in `bulk-run.js`). Errors are `{code, message}` plus `aipt_usage` after a billed call, `stage` after a write left mid-way, and `retry: true` for `aipt_batch_busy` / `aipt_prepare_busy` / `aipt_finalize_locked` / `aipt_terms_busy` / `aipt_job_busy`.

Recovery journal: the locator option `aipt_bulk_job_<post_id>_<lang>` (non-autoloaded, `{job_id, time, review?}`, stored by `AIPT_Bulk_Locator`) points to the record's durable job and is written before the first batch; inserted, replaced and deleted only with a compare on the stored row value (deletes of a live locator never match a tombstone). A finished job (`AIPT_Bulk_Jobs::complete`) first turns its locator into a tombstone `{job_id, done: {status, post_id}, time}` and is deleted only once the tombstone is stored (or no locator points to it); if the swap fails the completed job stays and answers the next request. Run token: `aipt_bulk_reset` removes all tombstones (site-wide, compare-and-delete on the values it read) and returns `since` (server time); the JS stores it from the first Start of a run, keeps it through Stop, and resets when the run finishes by itself or with "New run". `prepare` first asks `AIPT_Bulk_Jobs::locate` (before `AIPT_Runner::precheck`): a tombstone with `time ≥ since` is `skipped_done` (every mode, so Stop → Start never re-pays), a complete job returns its outcome, a `finalizing` job is busy while its finalize lock row is fresh else `needs_check`, a `none` job whose target changed (the writer's rule, `AIPT_Record::target_changed`) is `needs_check`. Then precheck (skip mode = `skip_existing`, duplicates stay eligible via `AIPT_Record::effective_mode`) and `prepare_or_reuse` under the named lock `aipt_bulk_prep_<post>_<lang>`, which reads the full locator again (a tombstone with `time ≥ since` → `skipped_done`; an older one is replaced by compare): another user/backend, or other options (mode, keep_date, and post_status for a new translation only) after a batch was paid → `needs_check`; other options with nothing paid → replaced; else `reuse` with `next_index` (first unsaved batch, from the batch option names alone). `AIPT_Bulk_Jobs::settled()` is the one stage branch (`complete` → outcome, `finalizing` → busy/`needs_check`, else null) for `locate`, `prepare_or_reuse`, `batch` and `finalize`. `finalize` handles the same stages (a retry never writes twice; `aipt_finalize_interrupted` from a takeover of a stale lock is `needs_check` too), then `AIPT_Runner::revalidate_before_write` (a refusal is `{status: review}`, job and locator kept with the message), then `AIPT_Pipeline::finalize` (a busy pair or pending target is `skipped_locked`/`skipped_pending`, job and locator kept for the next Start); a missing job whose tombstone names it returns the tombstone's outcome (batch and finalize send `post_id` + `target`; the target language is sent as `target`, never `lang`, because Polylang reads a `lang` request parameter as the request's language). Replacing or discarding a job runs under that prepare lock and returns `aipt_job_busy` while its finalize lock or one of its batch lock rows is fresh (a discarded job that turns out complete is settled to a tombstone instead). `translate_batch` re-reads the batch and the job past the request caches under the batch lock (`AIPT_Job::get_fresh`): a job gone is `aipt_job_expired`, one finalizing/complete is `reused`, never a paid call; `AIPT_Finalize::run` runs its checks on a fresh read under the finalize lock. `pending` ignores tombstones, finishes complete jobs (listed once with their outcome), flags `target_changed` and gives each row the job's source language as `from` ("Translate anyway" runs with it). Discard is allowed for any administrator (stale entries can always be cleared); "Translate anyway" (discard, then that record alone in overwrite mode after a confirmation) only for the job owner. `bulk-run.js` (the run engine, `window.aiptBulkRun`, started by `bulk-ui.js` with the DOM/`localStorage` helpers; one error policy, `stopReason`, also used by `bulk-strings.js`) runs terms pairs slice by slice, one at a time, then records through 1–3 workers (never two languages of one source at once, never a child while its parent is queued or in flight); fatal codes stop the run at once, 401/403 (also a terms `error_code`) pause it. `bulk.js` (form, Estimate/Start, run token, pending panel) stores only the form values and the run token in `localStorage`.

### Auto-translate on publish (`AIPT_Auto`)

Hooked on `wp_after_insert_post` (after REST terms/meta, so the multilingual plugin has set the language). It only schedules — never translates in the save request — when: the post becomes `publish` (`$post_before` missing or not `publish`), not `WP_IMPORTING`, `AIPT_Pipeline::is_writing()` is false, `auto_translate` is on (`AIPT_Settings::auto_enabled()`, a raw option read), the type is enabled, its language is the adapter's `default_language()`, the `_aipt_auto_scheduled` marker is absent (plugin-written posts always carry it; the adapter keeps it out of the multilingual plugin's meta sync), and a selected language lacks a real translation (`translation_state()` other than `translated`). It then adds the marker and one `aipt_auto_translate` single event two minutes later (`DELAY`, so the block editor's second metabox save lands first; args: post ID, user ID). A post that becomes `future` instead stores the scheduling user in `_aipt_auto_user`; at publish the user is the current one if they can edit the post, else that meta, else the author. The handler re-checks, runs as that user (restoring the previous user in `finally`), and per language: `check_source` / `missing_parent` (no cost) → `AIPT_Terms` for missing terms and their ancestors → `missing_terms` → `translate_post(holder: auto, skip_existing, publish, source date)`. Errors go to `error_log` and stop the post; a skipped language (parent or terms missing, no `edit_terms`, pair locked, target pending) is logged and the next one runs. No retries; existing translations are never updated. `auto_languages` is `'all'` (every box ticked, also covers languages added later), a list, `[]` (none) or null (never saved = all). Known limits are listed in the class header.

### Item path addressing

`AIPT_Extractor` assigns every translatable string an id (`s0`, `s1`, …) and a path that `AIPT_Writer` later resolves:

- `['post', 'title' | 'excerpt']`, `['post', 'content', N]` (HTML chunked at 8 KB on closing block tags; concatenating chunks restores the original). After chunking, `AIPT_Blocks::mask()` replaces each block delimiter comment in a chunk with a `[[AIPT-B<n>]]` token (maps in the job's `blocks`, keyed by N; absent for posts without blocks); the writer restores them after kses with `AIPT_Blocks::restore()`, so block JSON is kept out of the model's input and restored from the source. Reusable block refs (`<!-- wp:block {"ref":N} /-->`, ref-only JSON) in the assembled content (translated, unsent or source chunks; not a content kept by safe mode) are pointed at block N's target-language translation when it has one (`AIPT_Block_Refs::remap`); on render, `AIPT_Block_Refs::filter_render` (`render_block_data`) does the same for a `core/block` against the language of the global post being rendered, so a translated page shows the target-language block whichever was translated first. A chunk that already contains `[[AIPT-B` gets tokens with a suffix it does not contain (`[[AIPT-B<letters>-<n>]]`, entry `['prefix' => …, 'map' => …]`); a chunk the delimiter pattern cannot scan (PCRE error) is not sent (`['fallback' => true, 'source' => chunk]`, no item) and the writer puts its source back at its index (`AIPT_Blocks::unsent_chunks()`), counted as a fallback. The first chunking pass never splits inside a delimiter (a `</p>` in block JSON joins the pieces again). A chunk whose tokens came back changed keeps its source text; a new translation is then left as a draft whatever `post_status` was requested, and the write is reported as `aipt_written_with_warning` with `['post_id' => …]` (the same code a failed final status/slug update in `finish_new_post` returns: written, with a warning; when both happen the fallback is a second message of that error and the pipeline joins all messages).
- `['blockattr', N, n, ...keys]`: a text value in the JSON of delimiter n of content chunk N (`AIPT_Block_Attrs::extract()`, called by the extractor only for chunks that are sent, so a content kept by safe mode sends none). Text keys per block come from `AIPT_Block_Attrs_Config::get()`: `aipt_lang()->block_text_attributes()` on WPML (its `wpml-gutenberg-config` option), else (Polylang, or that option empty on WPML) the `wpml-config.xml` files of active plugins/mu-plugins/themes parsed like WPML (transient `aipt_block_attrs`, keyed by a hash of file list + mtimes, 1 day), merged with block.json `"role": "content"` string attributes without `source` whose name `is_non_text_name()` accepts (the name is split into words on camelCase/`_`/`-`; a word of `NON_TEXT_WORDS` such as url, link, target, type, id drops it unless the last word is one of `TEXT_WORDS`: `linkTarget` dropped, `linkText` kept) (WP 6.7+ marks URLs, targets, types etc. as content too; such keys carry `aipt_source => block_json`, which a wpml-config definition of the same key replaces, and their lowercase ASCII one-token values are skipped), then the `aipt_block_text_attributes` filter (`$config, $backend`). Key semantics follow WPML's StringsInBlock\Attributes (exact/wildcard/regex keys, any `type` = not text, `children` or match-all for arrays, `encoding: json` values marked by a `'#json'` path segment); URLs, paths, anchors, e-mails and numbers are never items (a value starting with `#`, `?` or `/` is a fragment/query/path only without whitespace, so "#1 Best choice" is text). Before its item loop the writer replaces `$job['blocks']` with `AIPT_Block_Attrs::apply()` (translations sanitized with `AIPT_Writer::sanitize_translated()` for users without `unfiltered_html`, then `&amp;` turned back into `&`: values are plain text), which rebuilds each such delimiter in the chunk's map: JSON re-encoded with core's `serialize_block_attributes()` when that reproduces the source JSON, else a targeted replacement of `"key":<old>` found exactly once; the result must parse (`parse_blocks`) as the same block with only those values changed, else the source delimiter is kept. Empty translations and values that cannot be written back keep the source silently (no fallback warning).
- `['meta', meta_key]` (Yoast SEO keys and the `extra_meta_keys` setting: plain-text meta keys, one per line in Advanced settings, sanitized by `AIPT_Settings_Advanced`; carried in the job's `meta` only when the source value is a non-empty string, so an empty source never clears the target)
- `['woo', 'attr', key, 'name' | 'value', i]` (WooCommerce custom attributes, see below)
- `['acf', field_key, row_index, sub_key, ...]`, with a `['#chunk', N]` suffix for long WYSIWYG values

ACF values are read raw (`format_value = false`) — repeater/flexible rows keyed by sub-field keys with `acf_fc_layout`, the exact shape `update_field()` accepts. The full ACF tree travels in the job; translated strings are substituted into it by path.

### WooCommerce (`AIPT_Woo`)

When WooCommerce is active, products get items for their non-taxonomy `_product_attributes`: the label (`name`) and each trimmed ` | `-separated option of `value` (index `i`). Taxonomy attributes (`pa_*`) are terms and copied verbatim. The job carries the raw source array as `woo` (`[]` or `['attributes' => …]`); `AIPT_Woo::write()` (called by the writer right after meta) rebuilds `_product_attributes` from that snapshot with the same keys/position/flags, translated options (`sanitize_text_field`, source option when missing), and the **source** name; the translated name goes to post meta `attr_label_translations[$target][$key]` on the translation (merged; WooCommerce Multilingual's label storage). Safe mode keeps a filled target option at the same index and an existing label (recorded in `preserve` through the same `AIPT_Safe_Merge::preserve_value()` / `preserved_value()` helpers as post, meta and ACF paths) for keys the source has; the key set always follows the source (WooCommerce Multilingual rebuilds the translation's attributes from the original's keys, so target-only attributes are dropped, also in safe mode). Jobs without `woo` are a no-op.

### Writer ordering invariant

`AIPT_Writer` order matters and must be preserved: `suspend_sync` → insert/update post → `begin_post` (Polylang: set the language) → ID remap (relationship/post_object/page_link/taxonomy fields remapped to target-language equivalents) → meta → WooCommerce attributes (`AIPT_Woo::write`) → ACF → taxonomies → `commit_post` (group link, verified) → `finish_new_post` → `restore_sync` in `finally` (idempotent), so the multilingual plugin's sync-on-save never touches a half-built post. Only a new translation gets its requested status and a re-checked slug in `finish_new_post` (it is inserted as a draft, so publish hooks see the finished, linked post). Before writing, the writer re-reads `translation_state()` and aborts with `aipt_target_changed` when it differs from the job's `target_state` (unless the job updates a real translation the user confirmed and it is not a duplicate now); `pending` always aborts. Slugs of new posts and terms come from `AIPT_Slug` (entity-decoded, accent-stripped, Cyrillic transliterated by a built-in table for the target language (KMU 2010 for `uk`, a Russian table otherwise) before `sanitize_title` so no letter a site's one-language transliteration plugin misses ends up percent-encoded; a cross-language collision gets `-{lang}` instead of `-2`). Model output (and only model output — never values copied verbatim from the source) is run through `wp_kses_post` for users without `unfiltered_html`.

### Safe mode (updating an existing translation)

`mode === 'safe'` keeps filled target fields. Three coordinated path lists flow from extractor to writer through the job: `preserve` (target value exists — keep it), `overwrite` (target empty/missing — replace in full), `flex` (flexible-content fields merged row-aligned by layout instead of replaced wholesale; see `AIPT_Safe_Merge::align_flexible_rows`). ACF fields also have three user-facing states via settings overrides: translate (default), copy, skip ("Don't touch") — policy decided in `AIPT_ACF_Schema::action()`.

### Concurrency & state

- `AIPT_Job` implements locks as `INSERT IGNORE` rows in `wp_options` (mirroring `WP_Upgrader::create_lock`), with stale-takeover by timestamp, because `add_option()` is not atomic. Lock reads bypass the object cache deliberately.
- `AIPT_Usage` (cost log + totals in options, capped at 100 entries) serialises concurrent batch writes with a global named lock; entries are idempotent per `job_id` (subsequent batches accumulate into the existing row).
- Pair lock (`AIPT_Job::acquire_pair_lock`, row `aipt_pair_lock_<group_id>_<lang>`, group_id = `aipt_lang()->group_id()`: smallest post ID of the translation group on Polylang): `translate_post()` holds it for a whole record (`RECORD_PAIR_LOCK_TTL`, 30 min, refreshed after each batch; holder `cli` or `auto`), the editor only around the write in finalize (5 min). The row stores the holder's TTL and role, so contenders apply the holder's expiry and the editor can say who is busy. The pipeline calls `aipt_lang()->refresh()` right after taking it, before re-checking the target.
- Jobs without the `usage_recorded_per_batch` marker are pre-1.3 jobs and keep finalize-time usage aggregation — don't break that upgrade path.

### Gateway

`AIPT_Gateway` talks to `https://ai-gateway.vercel.sh/v1/chat/completions` (OpenAI-compatible). It requests JSON mode, retries once without `response_format` on HTTP 400, retries missing keys once in a fresh conversation, and strips markdown fences from replies. Usage (`tokens_in`/`tokens_out`/`cost`) accumulates per `translate_map()` window. The supported-model list lives only in `AIPT_Settings::model_catalog()` — select labels, the cheat-sheet table, sanitization, and the per-model `reasoning.effort` sent by the gateway all derive from it.

## Conventions

- WordPress style: tabs for PHP/CSS indentation, same-line braces, `array()` syntax, strict comparisons, early returns.
- Prefix everything global (functions, hooks, options, script handles, CSS classes) with `AIPT_`/`aipt_`. Class files: `includes/class-aipt-<name>.php` → `AIPT_<Name>`. Keep the bootstrap small; new behavior goes in a focused class under `includes/`.
- AJAX handlers check nonce + capability first (`AIPT_Metabox::guard()`); sanitize request data, escape at render time. User-facing strings use the `ai-polylang-translator` text domain (translations in `languages/`: en source, ru_RU, uk).
- The API key is write-only in the UI: empty input keeps the stored key, and it is never echoed back into the form.
- JavaScript stays vanilla and admin-page compatible (no build step).
