# AI Translator for Polylang & WPML

WordPress plugin that translates posts, pages, WooCommerce products, taxonomy terms, Yoast SEO fields and ACF fields into the other languages of a Polylang or WPML site, using models served through the Vercel AI Gateway. The multilingual plugin keeps owning languages, translation groups and sync; this plugin only supplies the translated text.

Plugin slug, text domain and file names stay `ai-polylang-translator` for compatibility with existing installs.

## Requirements

- PHP 8.1+, WordPress 6.0+
- Polylang **or** WPML (Multilingual CMS). If both are active, the plugin refuses to translate and shows a notice until one is deactivated.
- A Vercel AI Gateway API key
- Optional: WooCommerce (+ WooCommerce Multilingual on WPML), Yoast SEO, ACF

## Settings (Settings > AI Translator)

- **Status / Enable AI Translator**: the global switch. Off parks the plugin so the multilingual plugin's own translation tools can be used alone: no AI Translation box, every AJAX request refused, no automatic translation (queued events do nothing), `wp aipt` refuses to start and a running bulk command stops before the next record. Settings, the cost log and the API-key test stay available; turning it back on needs no migration.
- **API**: key (write-only: an empty field keeps the stored key), key test, model, site context for the prompt.
- **Post types**: which public post types (including `product`) and reusable blocks (`wp_block`, inserted into pages by reference; translate them so translated pages do not show the source language) get the AI Translation box and can be translated. A translated page's `wp:block` refs are written pointing at the target-language block when it has a translation, and on the front end a translated page shows the target-language block when it has a translation, whichever was translated first.
- **Automatic translation**: translate a post in the default language when it is first published (off by default), target languages.
- **Advanced**:
  - *Extra meta keys to translate*: plain-text custom fields, one meta key per line (e.g. a price-unit label). Only non-empty string values are sent; an empty source value never clears the translation's value.
  - *Copy meta keys*: custom fields copied to translations as they are (not translated), one meta key per line; a trailing `*` matches a prefix (e.g. `_kad_post_*` for Kadence page settings). Applied when a translation is created or updated (also in safe mode): for every source key that matches, the translation's values are replaced with all source values. Translated keys (extra meta keys, Yoast SEO, ACF, WooCommerce attributes) and internal keys (`_thumbnail_id`, `_wp_page_template`, `_edit_lock`, `_edit_last`, `_wp_old_slug`, `_aipt_*`, the multilingual plugin's own keys) are never copied.
  - *Copy term meta keys*: the same for term meta (e.g. `thumbnail_id`), applied when a translated term is created or linked by `wp aipt translate-terms`, the bulk page or automatic translation.
  - *WPML translation editor* (WPML only, default on): see below.
- **ACF fields**: per-field translate / copy / don't touch overrides.
- **Cost log**: the latest 100 translations with tokens and cost, plus totals.

## Usage

- **Editor**: the "AI Translation" box on a post lists the target languages. A new translation is created as a draft; an existing one asks for confirmation before it is overwritten, or can be updated in safe mode (filled fields of the translation are kept). Failed steps can be retried.
- **Automatic translation on publish**: one background event two minutes after the first publish translates the post's missing terms, then the post, into every selected language without a real translation. Existing translations are never updated.
- **Bulk translation page** (Settings > AI Bulk Translation): terms, then posts, products and pages from wp-admin, without SSH. See below.
- **WP-CLI**: `wp aipt translate` (bulk posts, resumable, `--dry-run` shows the estimated cost), `wp aipt translate-terms` (term names and descriptions) and `wp aipt translate-strings` (WPML String Translation strings, see below). See `wp help aipt translate`.

## Bulk translation without SSH

Settings > AI Bulk Translation (administrators, `manage_options`) translates whole post types and taxonomies from wp-admin. Choose post types (those enabled in the settings; published posts in the source language), taxonomies (translated ones in which you can create terms; the term count follows the chosen source language, and a taxonomy without terms in it is greyed out with "(0)"), source and target languages, what to do with existing translations (skip, the default; update in safe mode; overwrite, with a confirmation box), whether new translations are published (sources that are not public stay private, scheduled or draft, as with `wp aipt translate --publish`) and keep the source dates.

- **How it works**: the open browser tab drives the run, one request at a time per stream: each selected taxonomy × language first (one short request per group of missing terms that fits in two API calls — up to 120 short names, fewer with long descriptions — created right away), then every post × language: prepare → one request per block → save. There is no queue, cron or background process; the database is the state. Every finished block is saved in a durable job (`aipt_bulk_job_<post>_<lang>` points to it), so whatever happens to the tab, the connection or the computer, a block that was saved is never paid for again. The one residual risk is a single block whose reply was billed but never saved because its request was killed mid-flight.
- **Keep the tab open** and the computer awake until the run ends (roughly 2 hours for 1,500 products into one language). Leaving the page asks for confirmation.
- **Stop and resume**: Stop lets the requests of the records in progress finish (including their retries) and starts nothing new. Start again to continue the same run: records finished in this run are skipped in every mode, also in safe and overwrite mode (each finished record leaves a small marker, and the tab keeps a run token from the first Start); unfinished records resume from their saved blocks; in skip mode, records translated earlier are skipped too. A run ends when it finishes by itself or when you click **New run**; the next Start then begins a new run, which in safe or overwrite mode translates every selected record again. The finished-record markers are site-wide: a new run started by any administrator clears them for everyone, so run one bulk translation at a time. The run stops after 5 errors in a row, at once on errors no record can get past (plugin disabled, no API key, expired page, missing permissions, a multilingual-plugin API failure), and when the API key is rejected (also during terms).
- **Estimate first**: Estimate runs the same pre-checks as a real run and the `wp aipt translate --dry-run` cost estimate, without API calls or writes: per status counts (would create, would update, skipped and why), characters and cost, terms included.
- **Needs manual check**: a record is never written automatically when a previous run started writing it and did not finish (the request died inside the write), when its source was edited, changed status or lost its parent or term translations after its blocks were translated, when its translation was created or removed elsewhere after its job was prepared, or when its unfinished job belongs to another user or other options (mode, publishing, dates). Such records are listed in the "Needs manual check" panel with links to the source and, if one was written, the translation. *Translate anyway* (only for the user who started the job) asks for confirmation, discards the job and translates that one record again in overwrite mode (the blocks are paid again); *Discard* (any administrator, so stale entries can always be cleared) removes the job. The panel also lists unfinished jobs of earlier runs, which resume on the next Start.
- **Order**: terms first (product categories and tags, `pa_*` attribute terms, categories), then products, then pages. Posts whose terms or parent page have no translation are skipped (`terms not translated`, `parent not translated`) and picked up by the next Start once they do. Pages run parents first: a child page never starts while its parent is still queued or in progress. An interruption re-pays at most one group of terms (cents).
- **Parallel requests (1–3, default 2)**: records translated at the same time; two languages of the same source never run at once. Each stream occupies one PHP worker for up to a minute per block, so keep 1–2 on shared hosting, where visitors need the remaining workers. Terms always run one request at a time.
- **Soft limits**: the cost limit (USD) stops starting new records and blocks once the run's cost reaches it; records whose blocks are all translated are still saved. The cost counter on the page is a convenience for this tab (it starts at zero on every Start); the cost log on the settings page is authoritative, per record.
- **Log**: errors, warnings, skips and records needing a check are listed with their reason; the details of pre-check and estimate rows use the same English wording as the WP-CLI log.
- **Server notes**: requests continue after the tab goes away (`ignore_user_abort`), best effort: PHP-FPM time limits still apply, and on LiteSpeed set `noabort` for `admin-ajax.php` (LiteSpeed otherwise stops PHP when the client disconnects).
- **Before and after**: back up the database before a large run; do not translate the same posts with WP-CLI or the editor at the same time, and keep automatic translation off during the run; purge page caches when it ends (the `aipt_translation_written` hook fires per post).
- **Strings (WPML String Translation)**: a separate section at the bottom of the page translates WPML String Translation strings without SSH, like `wp aipt translate-strings`. It lists the domains (WPML "contexts") that have strings in the chosen source language, with the number of strings and, per selected target language, how many have no finished translation. Tick domains and languages, optionally *Update existing translations* (= `--mode=update`), then *Estimate* (dry run: no API calls, no writes; counts per status, characters and cost) or *Translate*. The tab sends each domain × language in short requests of a few dozen strings each (at most two gateway batches, so an interruption re-pays at most one request), shows a summary row per domain × language (created, updated, skipped and why, errors, cost) and logs every translated, would-be-translated or failed string with its text or reason. Same rules as the command: placeholders and HTML are kept, a translation with changed placeholders is not saved, empty and placeholder-only strings are skipped. Stop ends the run after the current request. On Polylang, or WPML without String Translation, the section only says that strings are not supported.

## WPML

On a WPML site the plugin writes only translated text; language assignment, translation groups (trid), TM status, media and WooCommerce Multilingual sync stay WPML's job and are reached only through WPML's public hooks. If a hook the plugin relies on is missing (for example after a WPML update), nothing is written and an error is shown.

- **Duplicates**: a WPML duplicate counts as untranslated. It is overwritten in place (same post ID, always in full, never in safe mode), the duplicate flag is removed, and automatic translation and `wp aipt translate` treat it as missing.
- **Pending translation jobs**: a language pair with translation work in progress in WPML (a Translation Management / Advanced Translation Editor job or a placeholder) is never written. The editor shows a message, WP-CLI and automatic translation skip the pair.
- **TM status**: after writing, the translation is marked complete in WPML Translation Management, so the Translation Dashboard shows it as translated.
- **Native editor setting**: when the first AI translation of a post is written, the original is switched to WPML's native-editor mode, so opening the translation in wp-admin does not redirect to WPML's translation editor. Can be turned off in Advanced settings.
- `wpml-config.xml` keeps the plugin's internal post meta out of WPML's custom-field sync.
- **Strings** (WPML String Translation): `wp aipt translate-strings --domains=<d1,d2> --to=<langs> [--from=<lang>] [--mode=update] [--dry-run] [--log=<path>] --user=<admin>` translates the strings of the given domains (WPML "contexts", e.g. `admin_texts_wpseo_titles` for Yoast SEO title templates, `yoast-seo-term-meta` for SEO titles and descriptions of terms) whose language is the source language, in batches, and saves each one as a finished WPML string translation. Placeholders (`%%title%%`, `%s`, `%d`, `{{…}}`) and HTML are kept; a translation whose placeholders changed is not saved and is logged as an error. Empty strings and strings with only placeholders or markup are skipped (WPML shows the original), and strings that already have a finished translation are skipped unless `--mode=update`. Same rules as `translate-terms`: `--user` (with `manage_options`), the global switch (checked before each domain × language), `--log` required unless `--dry-run`, exit status 1 when any string ended in error. Not available on Polylang. Without SSH, use the Strings section of Settings > AI Bulk Translation (see above).

## WooCommerce

Products translate their title, description, short description, Yoast fields and extra meta keys, plus the custom (non-taxonomy) product attributes: each option of an attribute value is translated, and the attribute label is stored where WooCommerce Multilingual reads label translations. Safe mode keeps filled options and labels of the attributes the source has; the set of attributes always follows the source (WooCommerce Multilingual rebuilds it from the original), so attributes that exist only on the translation are dropped. Taxonomy attributes (`pa_*`) are terms and are translated with `wp aipt translate-terms`. Prices, SKU, stock, images, variations and taxonomy links are synced by WooCommerce Multilingual on WPML.

## Gutenberg and Kadence blocks

Block delimiter comments (`<!-- wp:… {json} -->`, `<!-- /wp:… -->`) are replaced with `[[AIPT-B<n>]]` tokens before content is sent to the model, so block JSON is kept out of the model's input and restored from the source afterwards. If the model drops or changes a token in a part of the content, or a part's block markup cannot be masked, that part keeps its original text, a new translation is left as a draft, and the translation is reported with a warning.

Text kept in block attributes (the JSON of the delimiter, e.g. Kadence button labels or navigation link labels) is translated too: each text value is sent as a separate short item, and the translation is written back into that delimiter, with the rest of its JSON unchanged. Which attributes hold text comes from generic sources, never from a built-in list of blocks: the `<gutenberg-block>` definitions of the `wpml-config.xml` files that block plugins and themes ship (on WPML, the list WPML itself parsed from them; on Polylang, the files of the active plugins, mu-plugins, the active theme and its parent and `wp-content/polylang/wpml-config.xml`, re-read when one of them changes), plus the block attributes WordPress marks as content (`"role": "content"`, type string, not stored in the block HTML) whose names do not look like settings (URLs, link targets, types, slugs, icons, dates, sizes, IDs …); for those keys a lowercase one-word value such as `_blank` or `image` is never sent either. Keys typed as links, media or IDs, and values that are URLs, paths, anchors, e-mail addresses or numbers, are never sent. A site can add or remove keys with the `aipt_block_text_attributes` filter (see Hooks). Attribute texts are translated only together with the content (in safe mode, a kept content keeps its attributes too).

## Hooks

`aipt_translation_written` (`$post_id, $source_id, $lang, $created`) fires after every translation write, once meta, attributes and terms are saved, right after `clean_post_cache()`.

`aipt_block_text_attributes` (`$config, $backend`) filters which block attributes are translated: `$config` is `blockName => [attribute key => key config]` in the shape of the `key` part of WPML's `<gutenberg-block>` config (`[]` = text; `type` = not text, e.g. `link`; `search-method` = `regex` for a regex key, `*` is a wildcard; `children` for nested arrays; `encoding` = `json` for URL-encoded JSON values), `$backend` is `polylang` or `wpml`. Example: `$config['my/cta']['buttonLabel'] = array();`.

## Testing

There is no automated test suite. After a change, run `php -l` on every PHP file (see `CLAUDE.md` for the commands and the multilingual boundary grep), then check manually:

- **Polylang site**: Settings page (key test, cost log), the bulk page (estimate, a short run, Stop and Start again resuming an unfinished record, the "Needs manual check" panel), metabox new translation / overwrite / safe mode / retry, `wp aipt translate --dry-run` and one real record, `wp aipt translate-terms`, automatic translation on publish, the disabled state (box hidden, AJAX refused, cron no-op, CLI exits with status 1). Test with and without ACF and Yoast.
- **WPML site**: the same flows, plus overwriting a duplicate (flag removed, TM status complete), refusal while a translation job is pending, the Translation Dashboard showing AI translations as translated, the translation opening in the WordPress editor, a simple and a variable WooCommerce product (labels and options translated, variations, prices and stock synced by WCML), a Kadence page (block markup unchanged), and no PHP notices in cron and WP-CLI runs.
